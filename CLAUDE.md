# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Moxite Refinery is a Manifest V3 web extension that injects React components into Moxfield deck pages (`https://moxfield.com/decks/<deckId>`). It must work in both Chrome and Firefox.

## Commands

```sh
npm run dev        # rebuild dist/ on change (unminified, inline sourcemaps)
npm run build      # tsc typecheck + production build into dist/, then npm run zip
npm run zip        # dist/'s contents (not the folder) → "Moxite Refinery.zip" at the repo root
npm run typecheck  # tsc only
npm run lint       # oxlint (.oxlintrc.json)
npm run format     # oxfmt, rewriting files in place (.oxfmtrc.json)
npm run check      # typecheck + lint + format check
npm test           # build, then the Playwright tests against live Moxfield (opens Chromium windows)
npm run bump -- patch  # bump patch/minor/major and print the GitHub release tag command
npm run sign       # build, then sign on addons.mozilla.org as unlisted (scripts/sign.sh)
```

`npm run sign` reads `JWT_ISSUER` and `JWT_SECRET` (AMO API credentials) from `.env`, which is gitignored, and passes them to `web-ext` as `WEB_EXT_API_KEY`/`WEB_EXT_API_SECRET` so they stay out of the process list. Because `content.js` is minified, it also uploads the source as `git archive` of `HEAD`, so it refuses to run with uncommitted changes. The signed `.xpi` goes to `web-ext-artifacts/` (gitignored). AMO won't sign the same `version` twice, so bump it in `public/manifest.json` before each signing. It uploads to Mozilla, so don't run it unasked.

Version tags trigger `.github/workflows/release-firefox.yml`: AMO signs for self-distribution, then GitHub Releases hosts the signed XPI and `updates.json`. Keep `browser_specific_settings.gecko.update_url` pointed at the stable latest-release asset.

`npm run check` (types, lint, formatting) and `npm run build` are the static checks. `npm test` (`tests/`, `playwright.config.ts`) builds `dist/`, loads it into Playwright's Chromium in a fresh profile, and checks on the test deck below that each injection mounts in its place next to Moxfield's elements and shows something sensible; a failure usually means Moxfield changed the part of the page an anchor relies on. It needs a network connection, and the first time `npx playwright install chromium`. It runs headed because Moxfield doesn't load for headless Chromium, and Claude Code's Bash sandbox blocks Chromium's networking (DNS errors, connection resets), so run it outside the sandbox. When adding an injection, add a test for it to `tests/features.spec.ts`. oxlint runs its `correctness` rules plus the React plugin; oxfmt uses its Prettier-compatible defaults (100 columns, double quotes) and also formats the Markdown and JSON files. To try a change, load `dist/` as an unpacked extension (Chrome: `chrome://extensions` → Load unpacked; Firefox: `about:debugging#/runtime/this-firefox` → Load Temporary Add-on → `dist/manifest.json`), then reload the extension and the Moxfield tab after each rebuild.

## Architecture

**Build.** Vite library mode bundles `src/content/index.tsx` into a single IIFE, `dist/content.js`, because content scripts can't be ES modules. `public/manifest.json` is copied to `dist/` verbatim, so manifest changes go in `public/`, never `dist/`.

**Injection loop** (`src/content/injector.tsx`). Moxfield is a single-page app that replaces its DOM freely and navigates between decks without reloading, so components aren't mounted once. A `MutationObserver` on `document.body` (child lists, text, and `src` attributes; plus `popstate`) schedules a `reconcile()` per animation frame, which checks every injection's anchor and mounts, moves, unmounts or re-renders its component to match. A mounted component whose host has drifted from its `position` relative to the anchor is put back, since Moxfield inserts its own elements without regard for ours (e.g. appending a section's content when it expands, which would otherwise land after one of ours). Leaving a deck page unmounts everything; switching decks re-renders with the new `deckId`.

**Adding a component.** Create it in `src/components/`, taking `InjectionProps` (`{ deckId, target }`), and register it in `src/content/injections.ts` with an `anchor` function and an `insertAdjacentElement` `position`. `anchor` may return an array to mount a separate copy next to each element (each with its own `target`). An optional `target(anchor)` function reads what that part of the page is about from the DOM; the component gets it as `target` and re-renders when it changes. For example, the card details modal (a card's ⋯ menu → the card's name at the top of the menu, `[data-testid="card-options-view-details"]`) gets Moxfield's `card.id` from its image URL, `…/cards/card-<card.id>-normal.webp`, except for multi-face cards, whose URL is `…/cards/card-face-<card_faces[].id>-normal.webp` with a per-face id instead. Likewise the card group summary (`GroupSummary`) reads its group's total quantity from the group's header, which is the same link (`a.table-deck-row-link` with a `.fa-caret-down`) in every deck view; the mainboard is the deck view's first list of groups, and other boards ("Considering", i.e. the maybeboard, once expanded) follow it with the same headers. The modal's right-hand column is a run of sections (a header `div` with a bold title, the content, then an `hr.my-4`): rules text, the author's "Card Tags", "Card Legality" (`[data-testid="card-modal-legality"]`, its header) and "Rulings"; `CardTags` adds "Oracle Tags" (and "Art Tags") sections in the same style before "Card Legality". Below the boards, the deck list ends with a "Related cards" section, a list of collapsible rows ("Tokens (4) - Expand", "Considering (15) - Expand", the latter even when the maybeboard is empty; toggles `[data-testid="deck-list-related-cards-<name>-toggle"]`), and `DeckTags` adds its own "Oracle Tags" row in the same style at the end of the list: the oracle tags on at least 3 copies across the commanders and mainboard, by copies, most first, after those matching one of the author's Moxfield card tags (by `tagKey()`: case, spacing and hyphens ignored), which are green and link to a search per `tagSearch`. On decks the user can edit, clicking any other one creates a Moxfield card tag of its label on its cards (`tagCards()`, below), updates our copy of the deck (`addAuthorTag()`), and has Moxfield refetch its own. Clicking a group's header opens its menu ("Copy Section to Clipboard", "Buy All"), a Bootstrap dropdown portaled to the end of `body` that doesn't say which group it's for, so `src/content/groupMenu.ts` remembers the header last clicked (a capture-phase listener); clicking the header again closes the menu (Escape doesn't). `GroupTagMenuItem` adds "Delete Moxfield Tag" to it for groups that are one of the deck's Moxfield card tags, on decks the user can edit. The menu's contents unmount as it closes, so the confirmation (`DeleteTagDialog`, via `tagDeletionAtom`) is rendered by `DeckTags`. Moxfield replaces the whole modal on Prev/Next, so components anchored inside it remount. Anchors must use Moxfield's `data-testid` attributes (it has them on most of the deck page, e.g. the fixed bottom bar's `deck-floating-bar-root`), ids, tags and Bootstrap classes, not Moxfield's class names, which are partly hashed build output and change between deploys.

**Shadow roots.** Each component renders inside its own open shadow root on a `display: contents` host (its root's container is `display: contents` too, so components can sit inline) tagged `data-moxite-refinery="<id>"`. Moxfield's CSS doesn't reach components, so they style themselves (currently inline styles). Inherited styles do reach them through the host, though, so an injection's `hostClassName` can put Moxfield's Bootstrap classes on the host (e.g. `small text-muted`) to match the page's text exactly in both themes; `.text-muted`'s dark-mode colour isn't `--bs-secondary-color`, so the variable alone won't do. Mutations inside shadow roots aren't observed, so rendering doesn't retrigger reconcile.

**App-wide state** (`src/state.ts`). Every injected component is a separate React root, so state shared between them lives in Jotai atoms in one explicit `store`, which the injector provides to each root with `<Provider store={store}>`. Put new app-wide state there; non-React code reads and writes it through `store.get`/`store.set`. On every reconcile the injector calls `setDeckId()`, which updates `deckIdAtom`, loads the deck into `deckAtom`, then loads the deck's Scryfall oracle and art tags in parallel into `oracleTagsAtom` and `artTagsAtom` (each a `Map` keyed by `card.scryfall_id`, covering every board). Async state uses the `Loadable<T>` union (`idle | loading | loaded { value } | error { error }`), and a result is dropped if the user has moved to another deck by the time it arrives. Components read with `useAtomValue(...)` instead of fetching themselves. Art tags are fetched only while the `showArtTags` setting is on (turning it on loads them for the current deck); otherwise `artTagsAtom` stays idle. The project uses Jotai 3, which has no `loadable` util and whose async atoms need Suspense, hence the explicit status union.

**Settings** (`settingsAtom` in `src/state.ts`). The gear at the end of the deck page's fixed bottom bar opens a native `<dialog>` through `Dialog` (`src/components/Dialog.tsx`, also used by `GroupSummary`'s info button; `showModal()` puts it in the top layer, above Moxfield's stacking contexts; it styles itself with the `--bs-*` theme variables Moxfield defines, which reach into shadow roots). Change settings with `updateSettings()`, which saves them to `chrome.storage.local` (via `src/content/storage.ts`, a minimal typing of the API instead of `@types/chrome`); `loadSettings()` restores them at startup and follows changes from other tabs. Settings: `tagSearch` (`"scryfall"`, the default, opens a Scryfall search in a new tab; `"moxfield"` opens the deck's add-card search), `showArtTags` (default off), and `drawChanceThreshold` (a whole percentage from 1 to 99, default 95: `GroupSummary` shows the first turn with a higher chance of having drawn one of the group's cards, or, if that's after the turn cutoff, the chance by the cutoff), and the turn cutoff: `turnCutoffMode` `"bracket"` (the default) takes it from the deck's bracket via `bracketWinTurn()` (the first turn a table of that bracket can be expected to win: 9, 8, 6, 4, 4 for brackets 1–5, and 4 for decks without one), `"fixed"` uses `fixedTurnCutoff` (default 10); and for the info modal's draw tables (`DrawTable`), `drawTableFromOpeningHand` (start at 7 cards seen rather than 1, default on), `drawTableMaxCardsSeen` (7–99, default 30, within the mainboard's size) and `drawTableMaxCopies` (1–99, default 15, within the group's size), plus `heatBands`: where each of the tables' 9 colour bands (`src/components/heat.ts`, whose cells take white or black text, whichever has the higher WCAG contrast by colord) after the first starts, in percent, set with `BandSlider` and shared by both kinds of table (exact tables colour a cell by its share of its column's most likely outcome, cumulative ones by the chance itself). It defaults to 5, 10, 20, 40, 60, 80, 90 and 95. `parseSettings()` replaces an invalid stored array and drops stored keys that are no longer settings.

**Add-card search.** On decks the user can edit, the "Find and add cards…" bar (`#deckbox-search`) is present and its magnifying glass goes to `/decks/<deckId>/search?q=<query>`, which accepts Scryfall syntax including `otag:` and `atag:`. That page 404s on decks the user can't edit, so tag links fall back to Scryfall there. `navigateInApp()` moves there without a reload by `history.pushState` plus a dispatched `popstate`, which Moxfield's router follows (window events are shared with the isolated world); the card details modal closes on its own. `getDeckId()` returns null on the search page, so injections unmount there.

**Scryfall tags** (`src/content/scryfall.ts`). `fetchTaggableIds(scryfallIds)` sends the ids to `/cards/collection` (75 per request) to get each card's `oracle_id`s and `illustration_id`s. Multi-face cards may carry these per face instead of at the top level: transform cards have per-face illustrations, and reversible cards have per-face oracle ids too. `fetchTags("oracle" | "art", ids)` then streams the matching gzipped bulk JSONL (`oracle-tags` ~6 MB, `art-tags` ~13 MB) through `DecompressionStream`. It keeps every tag's metadata but only the taggings for the requested cards, adds each tag's ancestors with `inherited: true`, and merges a multi-face card's faces. The bulk URLs are versioned and cached by the browser for a year, so each file downloads about once per daily update.

**Deck data** (`src/content/deck.ts`). `getDeckId()` parses the deck id from the URL, excluding listing pages like `/decks/public`. `fetchDeck(deckId)` gets the deck as JSON from Moxfield's undocumented API, the same endpoint the deck page loads from: `GET https://api2.moxfield.com/v3/decks/all/<publicId>`. Requests are shared per deck id and kept for the life of the page, so a deck edited during the session stays stale until reload. Response facts that aren't obvious:

- `boards` has many keys (mainboard, sideboard, commanders, companions, maybeboard, …); any may be empty or absent.
- `board.cards` is an object keyed by `uniqueCardId`, not an array. `board.count` is total copies; each entry has its own `quantity`.
- `entry.card.scryfall_id` is the Scryfall id; `card.id` is Moxfield's own.
- `bracket` is the Commander bracket (1–5): the owner's `userBracket` if set, else Moxfield's estimate `autoBracket`, which the page doesn't display (its bottom bar shows "Bracket Info" with no number). `ignoreBrackets` marks a deck opted out.
- `deck.id` is a short internal id (used by other endpoints like `/v1/decks/<id>/primer`); the URL id is `deck.publicId`.

**Three kinds of "tags" — keep them apart.** They come from different sources, attach to different things and aren't interchangeable:

- **Moxfield deck tags:** labels on the deck as a whole, from Moxfield's fixed set of categories (e.g. "Combo", "Blink / Flicker", "Primer"). They're the deck response's top-level `hubs`: an array of `{ name, description }`, empty when the deck has none.
- **Moxfield card tags:** free-text labels the deck's author gives to cards _within that deck_ (e.g. "Assorted Removal", "Wincons"), used to group the deck list. Per deck, so the same card can have different tags in different decks. They're in the top-level `authorTags`: an object mapping card name → `string[]`. It's keyed by `card.name` (double-faced cards use the full "Front // Back" name), not by `uniqueCardId`. It covers every board, including the maybeboard, and untagged cards are simply absent. There are no tag fields on board entries or `card` objects.
- **Scryfall Tagger tags:** community tags from tagger.scryfall.com, global rather than per deck. Two kinds: oracle tags (what a card does, e.g. `ramp`; searched with `otag:` or `function:`) attach to an `oracle_id`, and art tags (what the art shows; `atag:`) attach to an `illustration_id`. Scryfall card objects don't include them. Get them from Scryfall search queries or the `oracle_tags`/`art_tags` bulk files (JSONL; one record per tag with `label`, `slug`, `parent_ids`/`child_ids` for its hierarchy, and `taggings`). A tag's `taggings` list only the cards tagged with it directly, not those of its child tags, so walk `child_ids` to get everything. For example, Sol Ring is under a child of `ramp`, not `ramp` itself, yet the `otag:ramp` search returns it, because search includes child tags. Moxfield's `card` objects have `scryfall_id` but no `oracle_id` or `illustration_id`, so matching a deck to Tagger tags needs a Scryfall lookup first.

**Editing card tags** (`editCardTags()` in `deck.ts`, behind `tagCards()` and `deleteCardTag()`). Moxfield itself only removes a tag one card at a time. Writes need the signed-in user's access token, which Moxfield keeps in memory only, in its Redux store. `public/main-world.js`, a plain-JS content script in the page's `"world": "MAIN"`, finds the store (the react-redux Provider's `memoizedProps.store`, a few fibers below `#js-reactroot`'s `__reactContainer$…`) and answers two window-message requests from `src/content/moxfieldPage.ts`, matched by id: `auth` (`state.user.accessToken`, which Moxfield refreshes itself) and `refresh-deck`, which dispatches Moxfield's own `GET_PUBLIC_DECK` and `GET_VIEWER_INFO` actions (shapes copied from its action creators; its middleware adds its sign-in) so it refetches the deck and its owner's tags into its store, as on page load. An in-app navigation away and back doesn't refetch; Moxfield keeps the deck in its store. Tags are saved through Bulk Edit to keep the requests few: `GET /v2/decks/<publicId>/bulk-edit` returns `{ boards: { <board>: text }, pricingProvider, … }`, one line per entry such as `7 Forest (WAR) 262 *F* #ramp #land synergy` (global tags are `#!name`), and `PUT /v3/decks/<publicId>/bulk-edit` with `{ boards, pricingProvider, usePrefPrintings, ignoreFlavorNames, allowMultiplePrintings }` saves it, answering `{ isSuccessful, deck }`; both use `allowMultiplePrintings=true` so separate printings survive the round trip. Lines are matched to cards by printing (`(SET) cn`, from the deck's entries), not by name: with `ignoreFlavorNames=false` a printing with a flavor name is written under it (Emiel the Blessed's SLD 2780 is `1 Swift Wind, Steed of She-Ra (SLD) 2780`). Bulk Edit has no `commanders` board, so commanders go through `PUT /v2/decks/<deck.id>/cards/<card.id>/tags` with the card's whole tag list (`["#deck tag", "#!global tag"]`), read from `GET /v1/decks/all/<publicId>/viewer`, whose `tags` maps card name → `{ tagName, isGlobal }[]`. Edits send `X-Public-Deck-ID` and `X-Deck-Version` (the deck's `version`, 0 in practice; `x-deck-version` responses aren't readable cross-origin). Moxfield's page doesn't see these edits and would save its stale tags and version over them, hence `refresh-deck`, falling back to a reload if the page world doesn't answer.

The types in `deck.ts` cover only the fields in use; the real payload is much larger. The API is unofficial and has changed shape between versions (v2 had boards at the top level), so type it loosely.

## Cross-browser constraints

- `permissions` has only `storage` (for settings), which shows no install warning.
- `host_permissions` lists every cross-origin host the content script fetches from (`api2.moxfield.com`, `api.scryfall.com`, `data.scryfall.io`) because Firefox content scripts need them; add new hosts there. Firefox grants MV3 host permissions at install from 127, but the floor is higher still (next point).
- `browser_specific_settings.gecko.data_collection_permissions` is `{ "required": ["none"] }`: addons.mozilla.org requires new extensions to declare what data they collect, and this one sends none to its developer. Firefox supports the key from 140 and Firefox for Android from 142, so those are the `strict_min_version`s (`gecko` and `gecko_android`); lower ones make `web-ext lint` warn.
- `web-ext lint` (`npx web-ext lint --source-dir dist --self-hosted`) still warns twice about `innerHTML` in `content.js`: React DOM's implementation of `dangerouslySetInnerHTML`, which this code never uses. Don't add uses of it.
- Check any new manifest key, permission or extension API against both browsers and the Firefox 140 (Android 142) floor.
- Content scripts run in an isolated world: wrapping `fetch`/`XMLHttpRequest` there won't see Moxfield's own requests (which use XHR), and its store isn't reachable, hence `public/main-world.js` in `"world": "MAIN"` (Chrome 111, Firefox 128). Vite's IIFE library mode takes one entry, so that script is plain JS in `public/`, copied verbatim.

## Testing in a browser

Test against https://moxfield.com/decks/7geKEhIPjEGtBTVUISFXjw ("Marina the Flickering Enchantress", Commander). It has a commander, a maybeboard, double-faced cards, deck tags (`hubs`) and card tags (`authorTags`), so it covers most of the response's shapes. Its owner can edit it at any time, so check counts against the live API instead of hard-coding them. Its author displays it as Image Stacks. Switching views (the View dropdown, or View Options) saves a per-deck view setting to Moxfield (a request to `api2.moxfield.com/v2/decks/all/<deck.id>/view-settings`), so don't do it unasked, and put it back afterwards.

Moxfield never gets past its "Loading Moxfield…" screen in a background tab (`document.visibilityState === "hidden"`), and the injector's `requestAnimationFrame` scheduling also stalls there. When automating Chrome, the tab has to be in the foreground before the page or the extension will do anything.

The add-card search bar only appears on the signed-in user's own decks, so the test deck above can't exercise `tagSearch: "moxfield"`; ask the user to sign in and open one of theirs. Content-script and manifest changes need the user to reload the extension at `chrome://extensions` (the automation can't open that page).

Don't close the Chrome tab you're given when a task is finished; leave it open and reuse it next time. Closing it removes the tab group, and the fresh tab created next opens in the background, which leaves Moxfield stuck loading until the user brings it to the front by hand.
